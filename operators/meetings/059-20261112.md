### Low-Bit Quantization: Pack/Unpack and `DequantizePacked`

**Motivation.** Low-precision quantization types — below 8 bits and especially below 4 bits — are becoming increasingly important. ONNX already has some support for 4-bit and 2-bit types. Newer formats include ternary values (effectively a sub-2-bit representation), 3-bit values, and a 1-bit variant that differs slightly from the usual 1-bit type. These matter most for running models locally on end-user devices such as laptops and desktops, where GPU memory is far more limited than in the cloud, while there is strong interest in running models with roughly 30 to more than 100 GB of weights. Low-precision formats are what makes many of these models run on edge devices. The goal is that all such models can be represented in ONNX.

**Pack/Unpack** ([#8576](https://github.com/onnx/onnx/pull/8576)) are two simple primitives that pack a tensor of low-bit values into a tensor of bytes without any storage overhead. For example, ten 3-bit values (30 bits) fit into 4 bytes. Today, 3-bit values are sometimes stored using the existing 4-bit types, which costs about 33% extra storage — a significant difference for multi-gigabyte models.

**`DequantizePacked`** ([#8677](https://github.com/onnx/onnx/pull/8677)) mainly targets the GGUF formats, which are popular and used by many available models. These formats are optimized for backend execution and do not just pack a single tensor: they combine several logical tensors in one byte stream, e.g. the quantized values, a scale, and a bias that is added. Scale and bias are often shared by blocks of quantized values, so the three logical tensors do not have the same shape.

Such a format can be expressed with primitive operators, including `Unpack`: split the byte sequence, unpack the parts, then apply scale and bias. However, the resulting subgraph becomes large. In practice, implementations do not want to execute these operators separately but use a fused kernel, and fusing a large subgraph is fragile, because the same logic can be written in many different forms. `DequantizePacked` is therefore not a primitive operator; its role is to represent known, more complex formats compactly.

**Which representation should exporters use, and which should backends optimize?** The two PRs overlap to some extent, even though they are described as complementary. The guidance from the discussion:

* If a format can be expressed with a single `Unpack` (without `DequantizePacked`), use `Unpack`. `DequantizePacked` is for formats that would need a subgraph of 10–20 operators.
* It should not matter much what the frontend generates. Mapping a single `DequantizePacked` to `Unpack`, or vice versa, is easy for a backend, as is any fusion of just two or three operators. A backend that only optimizes `Unpack` can expand `DequantizePacked`; a backend that already has fused kernels can use `DequantizePacked` directly.
* What the design avoids is forcing backends to recognize and fuse large subgraphs of 10–20 primitive operators.

**Typical usage.** Neither operator is expected to be used on its own. The usual pattern is a weight input to `MatMul`, `Attention`, or a Mixture-of-Experts operator that is unpacked (or dequantized and unpacked) immediately before use. Hand-written kernels typically implement the quantized computation fused with the unpacking, so backends are expected to fuse this pattern. It effectively becomes part of the QDQ pattern, and existing QDQ fusion support should ideally be extended to handle QDQ with `Unpack` or `DequantizePacked`. Compiler-generated kernels can do the same fusion. Even without fusion, executing `Unpack` separately is not optimal but far better than executing 10–20 primitive operators.

### `LinearAttention` Input Types

For the opset 29 `LinearAttention`, some inputs appear to be required in FP32, while NPUs typically use FP16. The question was whether FP32 is required for accuracy reasons. Checking the operator's type constraints during the meeting showed that type `T` allows `float16`, `float`, and `bfloat16`. The FP32 requirement was seen in one of the Markdown documentation files; the exact location will be clarified offline on the PR. If FP16 support is needed, it would make sense to provide it.

### Merged Opset 29 PRs

The 1.24-milestone PRs merged since the list was shared were reviewed:

* **Numerically stable operators:** some computations can already be expressed in ONNX, e.g. as an exponential followed by a subtraction, but lose precision for specific floating-point values when implemented as separate operators. Commonly occurring fused operators of this kind are therefore added so they are implemented together: `Expm1` ([#8735](https://github.com/onnx/onnx/pull/8735)) and `Log1p` with a stable log-softmax decomposition ([#8710](https://github.com/onnx/onnx/pull/8710)).
* **Mean reduction for scatter operators** ([#8733](https://github.com/onnx/onnx/pull/8733)): the scatter operators already support reductions such as add and multiply; PyTorch also offers mean as a reduction, which is now supported.
* **int32 indices** ([#8692](https://github.com/onnx/onnx/pull/8692)): a gather operator previously supported only int64 indices and now also accepts int32, which is straightforward and useful.
* **`GroupedMatMul`** ([#8759](https://github.com/onnx/onnx/pull/8759)): support for transposed weights via a transpose flag; considered good.
* Minor extensions to `CausalConvWithState` (dilation, [#8687](https://github.com/onnx/onnx/pull/8687)) and `LinearAttention`.

Some PRs in the milestone do not change the specification but need Operators SIG approval, e.g. fixes to the reference implementation and documentation clarifications. These are expected to be straightforward and mainly need a reviewer.

The number of PRs has risen sharply with AI-assisted coding, with many first-time contributors. PRs therefore need to be prioritized even for review.

### Proposal: `GeGLU` as a Function Op

[#8266](https://github.com/onnx/onnx/pull/8266) (opened Aug 6, 2026) proposes `GeGLU` as a function op for opset 29; it is used in recent models such as Gemma 3 and Gemma 4.

**Standard filtering for new operators:** is the operation represented as an operator in any framework, and does it have an implementation as a function? `GeGLU` is defined as a function, so it passes the second test.

**General policy for small fused operators.** Operators like this are short fusions: users can write them as two operators instead of one, and backends can fuse them if they want. Two positions are possible:

* Keep the standard small, do not keep adding operators that are just compositions of two operators, and leave fusion to the backends.
* Define them as function operators, so that they exist in the standard while backends remain free to decompose them.

Proposed criteria for adding such an operator:

* It comes from the frameworks. For example, scaled dot-product attention comes from PyTorch. However, `GeGLU` has not been seen among the PyTorch ATen operators; the ATen operator set used by TorchDynamo should be checked.
* Other frameworks should be checked as well, not only PyTorch, e.g. GGML.
* Even if no framework has the operator, it may be added if it occurs repeatedly in recent models.
* A new consideration: some operators are added to research frameworks for people designing models, while others are added as fusions to inference runtimes such as llama.cpp, which compete with ONNX Runtime for local inference. Common support in inference frameworks, not only in deep-learning research frameworks, is also a reason to add an operator.

Scaled dot-product attention differs from `GeGLU` in complexity: depending on the variant, it spans 5–10 nodes (two `MatMul`s, a `Softmax`, possibly a bias), whereas `GeGLU` is a much simpler composition. This makes a hard and fast rule difficult.

**Outcome for `GeGLU`:** llama.cpp (the GGML operator list) supports it, it occurs in recent models, and `SwiGLU` is already part of ONNX (since opset 28). Adding it is therefore reasonable for this specific case; the PR still needs a review to make sure it is correct. Whether such operators should be added in general remains an open question.

### ONNX Specification and Runtimes

Changes to operators go into the ONNX specification, which is distinct from the backends that implement it. ONNX Runtime is one such backend; others include OpenVINO (Intel) and TensorRT (NVIDIA), which can be used through ONNX Runtime or independently. Each backend is updated separately to support new specification changes.
